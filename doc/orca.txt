*orca.txt*  Branch review for orca deliverables, in your own editor.

                                                        *orca* *orca.nvim*

orca.nvim opens a branch review — the merge-base diff of a deliverable
branch against trunk — inside your fully-configured Neovim: your LSP, your
colors, your muscle memory. It is the human half of review; an orca run's
independent reviewer already attacked the diff mechanically, and this is
the look-through before `git merge --no-ff`. Comments you write on the way
persist under `.orca/` and flow back into the run (|orca-notes|).

It requires an orca-managed repository: `.orca/` must exist at the repo
root. In a repo without one, |:OrcaReview| refuses with a pointer at
`/orca:init`. No required setup(), no dependencies.

==============================================================================
COMMANDS                                                        *orca-commands*

                                                                  *:OrcaReview*
:OrcaReview [{range}]
        Start (or restart — at most one session exists) a review session.
        {range} is `<base>...<head>`, always in the three-dot merge-base
        sense: only what the branch changed, never what trunk gained since
        the branch point (a two-dot `<base>..<head>` is refused by name).
        A bare `<base>` implies `...HEAD`; no argument
        defaults to `<trunk>...HEAD`. Trunk resolves in tiers: in a
        linked worktree, the symbolic HEAD of the common git dir (the
        bare repo's HEAD in orca's bare-with-worktrees layout); in a
        normal checkout, the branch `origin/HEAD` names (preferring its
        local twin), else the first of `main`/`master`/`trunk` that
        exists locally. A range that doesn't resolve leaves a running
        session exactly as it was; only a good one replaces it.

        `<head>` must be the commit checked out where you run it: the right
        side of every pair is the working tree, so any other head would
        show content it doesn't have. For a branch checked out in another
        worktree, the refusal names that worktree.

        The changed files populate the review panel (|orca-panel| — a
        bottom strip, one line per file with its `M`/`A`/`D`/`R` status)
        and the first file's diff pair opens immediately. <CR> on a panel
        line opens that file's pair: the working-tree file on the right —
        a real buffer, LSP attaches, editable — and the merge-base version
        on the left in a read-only scratch buffer. Native diff mode drives
        both, so |]c|, |[c|, |do| and |dp| work as everywhere else.

        Any existing review notes for the branch load with the session
        (|orca-notes|): comments from an earlier sitting reappear at
        their anchors, and resolutions orca wrote back render under them.

        Edge cases: added files diff against an empty left side; deleted
        files show the removed content on the left with an empty right
        (there is no working-tree file); renames are detected and load the
        old path at the merge-base; binary files open plainly, marked
        `(binary)` in the list. A dirty working tree is diffed as-is —
        what you review is what would merge.

        The pair follows navigation. Entering a changed file by any route
        — a fuzzy finder, |gd|, plain |:edit| — opens its diff pair around
        the window you landed in, panel selection synced. Wandering off
        to a buffer outside the review collapses the pair (left split
        closed, diff mode off); the session stays alive, and the panel,
        |:OrcaReviewNext|, or entering any changed file resumes the walk.
        When the file you land on can use the pair already on screen, the
        pair's two windows stay where they are and only their contents
        change, so a jump never reflows the layout. Taking a pair down
        uses |:diffoff!|, which ends diff mode for the whole tab page: a
        diff of your own in the same tab would be compared against the
        pair anyway, so review in a tab of its own if you keep one.

                                                             *:OrcaReviewClose*
:OrcaReviewClose
        End the session: review notes saved, diff mode off, the panel
        destroyed, scratch buffers wiped, keymaps removed — the session's
        global ones handed back to whatever they meant before it started.
        This is the only way to be rid of the panel. Quitting Neovim
        cleans up the same way (the only thing that persists is the notes
        file, and persisting is its job).

                                            *:OrcaReviewNext* *:OrcaReviewPrev*
:OrcaReviewNext
:OrcaReviewPrev
        Move to the next/previous changed file, tearing down the current
        pair and opening the new one. The walk follows the panel: a file
        a hidden group folded away is not one it stops on
        (|orca-hidden|).

                                                             *:OrcaReviewPanel*
:OrcaReviewPanel
        The panel's focus ladder: not there → open and focus it; there but
        unfocused → focus it; already focused → back to the file under
        review. The panel stays open throughout — it is pinned for the
        session (|orca-panel|) — so the key is a round trip, and pressing
        it twice leaves you where you started. With
        |vim.g.orca_panel_pinned| off, the third rung closes the window
        instead. Also available as the `panel` action in
        |vim.g.orca_mappings| (unbound by default).

                                                                 *:OrcaComment*
:[range]OrcaComment
        Create or edit the review comment anchored at the cursor line —
        or, with a visual selection or {range}, at that line range. On a
        line an existing comment covers, the comment opens for editing
        (which re-opens it: changed text means any previous resolution no
        longer answers it).

        Input happens in a borderless float placed exactly where the
        comment's virtual lines render, so editing looks like typing
        into the virtual text itself: the gap under the anchor stays
        open and grows with the text. Review comments are multi-line.
        (On Neovim 0.9 the input is a small scratch split at the bottom
        instead; same behavior.)

        The editor is the comment, not a draft of it: what you type is
        the comment's as you type it, and in the notes file (|orca-notes|)
        half a second later, on leaving insert mode, and on close — a
        crash loses nothing, and there is nothing to commit. Close it any
        way you like; `:w` flushes the save, so the habit is harmless and
        `:wq` closes. Leaving the float for another window closes it too,
        so the comment shows rendered, `#N` and all, as soon as you are
        back in the code. A new comment exists from its first word: close the
        editor before typing anything and nothing was created, no id used
        up. Opening a comment is not editing it — one orca resolved stays
        resolved until its text actually changes, and changing it back
        restores the resolution. Emptying a comment does not delete it:
        on close it keeps its last words, and |:OrcaCommentDelete| is the
        way to delete.

        The editor belongs to the file under it: the gap it hangs in is
        an extmark in that buffer, and where it sits on screen is that
        window's scroll. So the session's file changes — |:OrcaReviewNext|,
        the panel, the comment motions, a changed file entered by any
        other route — close it before the pair changes, keeping whatever
        it holds.

        Comments anchor to the working-tree (right) side of the pair
        only. The left buffer is a base-version scratch; a comment there
        ("this deletion was wrong") has no stable working-tree anchor and
        is politely refused, as are deleted and binary entries.

                                                           *:OrcaCommentDelete*
:OrcaCommentDelete
        Delete the comment covering the cursor line. An editor open on
        that comment closes with it. From inside the editor, it deletes
        the comment being edited (or discards a new one) and closes the
        editor; a `delete` key from |vim.g.orca_mappings| is mapped there
        too.

                                          *:OrcaCommentNext* *:OrcaCommentPrev*
:OrcaCommentNext
:OrcaCommentPrev
        Jump to the next/previous review comment, review-wide: file order
        (the panel's), then line, crossing into another file through its
        diff pair. Comments are orca's own extmarks — no native motion can
        find them — and positions are extmark-resolved at jump time, so
        they self-heal after edits. Clamps at the first/last comment with
        a message. Also available as `comment_next`/`comment_prev` in
        |vim.g.orca_mappings| (unbound by default).

THE PANEL                                                          *orca-panel*

The changed-file list lives in a buffer orca owns (`orca://review`,
filetype `orca-panel`), shown in a full-width strip at the bottom — the
quickfix window's old footprint, diff pairs keep full width. It is not a
quickfix list on purpose: quickfix is shared territory, and the verbs of
reviewing — |:grep| for a symbol's other uses, LSP references, test
runners — all push new lists, each one evicting the review from the
display. Nothing external writes into an orca-owned buffer, so the panel
survives everything short of |:OrcaReviewClose|; a foreign quickfix list
mid-session changes nothing.

One line per file: highlighted status letter, comment count, path
(renames as `old → new`), a `(binary)` marker where it applies, and the
file's `+n -n` line counts against the window's right edge. The current
file carries a full-line highlight and the panel's parked cursor, so
entering the panel always lands on it. Files with review comments show a
`*n` count between the status letter and the name — its column is
reserved on comment-less rows so names stay aligned — updating live as
comments are created, deleted, or loaded from an earlier sitting.

The line counts are `git diff --numstat`'s, so they read exactly as
|:OrcaReview|'s range does; their two columns size to the widest on show,
so the numbers stack down the panel. Both sides always show — a file that
only grows reads `+100 -0`, and the zero is the statement, so a blank in
the column never has to be told apart from a nothing. Only a binary file,
where git counts no lines at all, shows no numbers. They are held against
the edge by virtual text, so in a panel narrow enough for a path to reach
them they cover its tail rather than being pushed off the screen.

<CR> on a line opens that file's diff pair and focuses it, and so does a
double-click — on the line under the pointer, which is not always the line
under the cursor: the first press of the double-click focuses the panel and
moves the cursor there, so the click works from inside a diff pair too.
A click on the panel's 'statusline', or past the last row into empty space
(a hide-toggle routinely leaves some), opens nothing. The session's range
shows in the panel window's 'statusline'.

                                                     *vim.g.orca_panel_pinned*
The panel is pinned open for as long as the session lives. It is the
review's map — what is left, what you have already said something about,
where you are in the walk — and a review that has lost it is one
navigating blind, with nothing on screen saying so. So a window closing
under it (|:q|, |CTRL-W_c|, |:only|, a window-management plugin) puts it
straight back, re-rendered from session state and without taking your
cursor out of the file you were reading; so does a foreign buffer landing
in its window. |:OrcaReviewClose| is what ends it.

Set the variable to `false` to get the old closable panel back — closing
hides the view, the session and its content live on, and
|:OrcaReviewPanel| is the way back: >

        vim.g.orca_panel_pinned = false
<

What the panel lists is a view over the session's changed files, not all
of them: named groups — tests by default — fold away behind the last row
(|orca-hidden|). The panel's rows are that view, so a row number and a
file's position in the diff part ways as soon as something is folded.

Highlights, all with sensible defaults you can override:
`OrcaPanelAdded`, `OrcaPanelRemoved`, `OrcaPanelChanged`,
`OrcaPanelRenamed` (the status letters, and — for the first two — the
`+n` and `-n` line counts; linked to the builtin |hl-Added| /
|hl-Removed| / |hl-Changed| groups), `OrcaPanelCurrent` (the current
file's line, linked to |hl-CursorLine|), `OrcaPanelCount` (the `*n`
comment counts, purple by default), `OrcaPanelHidden` (the summary row,
linked to |hl-Comment|).

HIDDEN GROUPS                                                     *orca-hidden*

An orca run's diff is often mostly tests, and the look-through before
merge wants the source in front of it — so files matching a named group
fold away, and the panel's last row says so: >

         M *2 lua/orca/panel.lua
         A    lua/orca/filter.lua
         …    2 files hidden (tests) — <CR> shows
<
That row is the indicator and the control: <CR> on it toggles, and it
stays in both states (inverted — `showing everything — <CR> hides 2`), so
the way back is never something you have to already know about. There is
no command; like the panel's `open`, this is an action on the panel.
`hidden` in |vim.g.orca_mappings| binds a key that works from anywhere
while the session lives, and `require('orca').toggle_hidden()` is the
scriptable entry point.

Hiding is a *view*, never a filter on the session. A hidden file is still
a full entry: |:edit| opens its diff pair, |:OrcaComment| anchors to it,
its comments reach the notes file and orca's addressing step. Three things
pin an entry visible whatever its group says:

        - a comment on it — once you have said something about a file it
          keeps its row (and its `*n`), and deleting the last comment
          folds it back
        - being the file you are currently in
        - being the last one left: hiding every file would open a review
          with nothing in it, so an all-tests branch shows everything and
          says why

                                                    *vim.g.orca_review_hidden*
Sessions start hidden. Set it to `false` to start showing everything (the
summary row is still there, offering to hide): >

        vim.g.orca_review_hidden = false
<
                                                    *vim.g.orca_review_groups*
A group is a list of globs, where the `/` decides what gets matched:

        `*_test.go`       no slash          the basename
        `tests/`          trailing slash    a directory, at any depth
        `spec/**/*.rb`    slash inside      the whole repo-relative path
        `/tests/`         leading slash     anchored at the repo root

`*` stops at a separator, `**` crosses it, `?` is one non-separator
character; `**/` matches zero or more directories, so `spec/**/*.rb`
takes `spec/a_spec.rb` as well as `spec/x/a_spec.rb`. Everything else is
literal. A rename folds away only when both
of its names match — a file moving out of `tests/` is exactly the change
you want in front of you.

The shipped `tests` group: >

        tests/  test/  spec/  __tests__/  testdata/
        *_test.*  *_spec.*  *.test.*  *.spec.*  test_*.py  conftest.py
<
`vim.g.orca_review_groups` replaces a group's list outright (copy the list
above to extend it) and `false` drops one; a new key adds a group. Every
defined group rides the one toggle, so a group you never want hidden is a
group you should not define: >

        vim.g.orca_review_groups = {
          generated = { '*.pb.go', 'package-lock.json', '__snapshots__/' },
          tests = false,                    -- stop hiding tests
        }
<
The defaults are deliberately literal — a too-greedy glob would silently
drop real code from every review in every repo, which is the one thing
this feature must never do. Fixture directories are absent on purpose:
fixture data is frequently the thing under review.

REVIEW NOTES                                                       *orca-notes*

Comments persist to a findings-adjacent JSON file that orca (the Claude
Code plugin's skills) consumes: >

        .orca/review-notes/<key>.json
<
`<key>` is the head branch with anything outside `[A-Za-z0-9._-]` replaced
by `-` (or the sanitized full range when head is not a branch — detached
HEAD, a sha). The repo root is the parent of the common git dir — the same
rule the orca skills use, so it works from inside any worktree of orca's
bare-repo layout and in a plain checkout alike. Everything is derived from
git state: quitting Neovim on Tuesday and reopening the worktree on
Wednesday finds the same file, with no launch-time handoff. The file is
created lazily on the first comment — a comment-less review leaves no
trace — and deleting the last comment removes it.

While the session lives, each comment is an extmark, so anchors ride
buffer edits (fixing nits during review is a feature). Every create, edit,
and delete rewrites the whole file from the extmarks' current positions —
always a complete snapshot, never an append. Alongside each line number
the file records the anchored line's text (`quoted`): numbers rot as soon
as fixes land, and the quoted text is how orca's fix agent finds the spot
after drift.

Comment text renders as virtual lines under the anchor, soft-wrapped to
the window's text width. Wrapping is display-only — recomputed at every
placement and on window resize, with the stored text never touched — and
your own line breaks are kept as paragraph breaks. A range comment shows
the `┃` gutter marker on every line it covers (Neovim 0.10+; older
versions mark the anchor line only).

The round trip: orca's addressing step converts each `open` comment into a
finding (severity High — if you bothered to write it, it matters), runs
the fix machinery, and writes `status` — `addressed`, or `answered` for
questions — plus a `resolution` note back into the same file, archiving a
copy with the run's artifacts. The next |:OrcaReview| renders resolutions
inline under their anchors. One file per branch is safe because the
workflow is sequential: orca runs, you comment, orca addresses, you
re-review — one writer at a time.

The file carries a `version` field (currently 1): plugin and skill ship
separately, and either side fails loud on a version it doesn't know —
orca.nvim then disables commenting rather than clobber a newer file. If
the file's recorded head is not an ancestor of the branch under review (a
recycled branch name), the load warns; delete the file to start fresh.

Highlights, all with sensible defaults you can override:
`OrcaCommentSign` (the `┃` sign column marker), `OrcaCommentText` (the
comment's virtual lines), `OrcaCommentResolution` (orca's write-back).

KEYMAPS                                                          *orca-keymaps*

The session's navigation verbs — `next`, `prev`, `panel`, `hidden`,
`close`, `comment_next`, `comment_prev` — are mapped globally for as long
as the session lives, because "which file is next" is a property of the
review and not of the window you happen to be standing in: they answer
from a |:grep| result, |:help|, a terminal, a file that is not in the diff
at all, the way the commands above always have. Whatever such a key meant
before is captured and handed back at |:OrcaReviewClose|.

The rest are buffer-local, set in the buffers the session owns (both diff
sides and the panel) and removed when it lets go of them, because there
they are the honest answer: `comment` and `delete` need a changed file's
working-tree line to anchor to, and `open` is the panel's alone.

One action ships bound, on two keys:

        <CR>            (panel only) open this file's diff pair
        <2-LeftMouse>   (panel only) open the clicked file's diff pair

In an orca-owned buffer neither shadows anything — the fugitive/oil
precedent for <CR>, and for the double-click the quickfix list the panel
replaced, where <2-LeftMouse> was <CR>; the native double-click there
(select the word under the pointer) is noise in a nofile list buffer.
A double-click needs 'mouse' to include the mode, as it does by default;
orca never sets it. Everything else ships unbound: orca never binds a key that doesn't already
mean what orca makes it do, and no native key means "next reviewed file"
or "comment this line" (`]q`/`[q` keep meaning the user's real
quickfix-next while a session is open). Restoring the old quickfix feel is
one line — counts work, `3]q` moves three files, clamped at the edge, and
|:cnext| goes back to meaning |:cnext| at |:OrcaReviewClose|: >

        vim.g.orca_mappings = { next = ']q', prev = '[q' }
<
|]c| and |[c| hunk motions are native diff mode — nothing to define.

The rest stays available as commands; bind what you use: >

        vim.g.orca_mappings = { comment = '<leader>rc', close = '<leader>rq' }
<
A `comment` binding maps normal mode (cursor line) and visual mode (the
selected range), in the session's own buffers. A `delete` binding deletes
the comment on the cursor line, same as |:OrcaCommentDelete|. A `panel`
binding rides the |:OrcaReviewPanel| ladder; `comment_next`/`comment_prev`
are |:OrcaCommentNext|/|:OrcaCommentPrev|. A `hidden` binding toggles the
hidden groups from anywhere at all (|orca-hidden|) — the one action with
no command behind it, since the panel's summary row carries it.

                                                          *vim.g.orca_mappings*
`vim.g.orca_mappings` reshapes the maps, read when a session starts (order
relative to plugin load never matters). A table overrides per action — keys
`next`, `prev`, `open`, `comment`, `delete`, `comment_next`,
`comment_prev`, `panel`, `hidden`, `close` — with `false` dropping that
one map; the
whole variable set to `false` drops them all (`hidden` is the odd one out:
it has no command, so dropping its map leaves the summary row as the only
way to toggle): >

        vim.g.orca_mappings = { next = ']q', prev = '[q' }   -- the old keys
        vim.g.orca_mappings = false                          -- commands only
<
A value is one key or a list of them. `open` ships as `{ '<CR>',
'<2-LeftMouse>' }`, so rewriting it says what open is — a plain string
binds that key and no other: >

        vim.g.orca_mappings = { open = '<CR>' }              -- keyboard only
        vim.g.orca_mappings = { open = { '<CR>', '<LeftRelease>' } }
<
The second is single-click-opens, which is yours to ask for rather than a
default: clicking the panel merely to focus or scroll it then opens a
file, and the extra release leaves a double-click in visual mode. Any
pointer key (a name containing mouse, release, or drag) takes its row from
the pointer; everything else from the cursor.

                                                                  *orca.setup()*
setup({opts}) is optional sugar over the same variable — `setup({mappings =
...})` assigns `vim.g.orca_mappings` and nothing else, so lazy.nvim's
`opts` works: >

        {
          "miguelbacalhau/orca.nvim",
          opts = { mappings = { comment = "<leader>v" } },
        }
<
Nothing requires calling it; the plugin stays lazy either way.

==============================================================================
INSTALLATION                                                     *orca-install*

Install with your plugin manager, like any other plugin. lazy.nvim: >

        { "miguelbacalhau/orca.nvim" }
<
No setup() call required, no dependencies — |orca-keymaps|, |orca-hidden|
and |vim.g.orca_panel_pinned| cover the only configuration. Any manager that installs
from GitHub works the same way; updates ride the manager's own update
flow.

Without a plugin manager, clone into Neovim's native packpath
(|packages|): >

        git clone https://github.com/miguelbacalhau/orca.nvim \
            ~/.local/share/nvim/site/pack/orca/start/orca.nvim
<
(the parent directory is `stdpath('data')` — check with
`:echo stdpath('data')` if yours differs), then generate help tags with
`:helptags ALL`. Updating is `git pull` in the clone; uninstalling is
removing the directory. Caveat: native packages need 'packpath' intact —
configs that reset it (some plugin managers do) ignore the clone
silently, in which case the manager route above is the fix.

If you use orca (the Claude Code plugin), `/orca:doctor` checks the
install and prescribes whichever path fits.

`:checkhealth orca` verifies the setup: git ≥ 2.5 on PATH, inside a git
repository, `.orca/` at the repo root, trunk resolvable.
